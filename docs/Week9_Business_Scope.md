# 第九周第二步：商品业务范围边界

更新日期：2026-11-04。对应旧版[圣火计划](../圣火文档.md)第九周的“超出商品业务范围 → 给出边界提示”。

## 处理规则

`backend/scope.py` 使用明确任务意图、商品目录名称及已有商品话题进行判断，不调用额外的分类模型。统一入口 `agent_invoke()` 在商品指代解析、答案缓存读取和图执行之前执行判断。

| 判断 | 示例 | 行为 |
| --- | --- | --- |
| 允许 | 参数、报价、售后、使用方法、商品对比 | 保留原问题，继续正式 Agent 流程 |
| 允许辅助对话 | 问候、身份、记录预算、读取备注、回顾商品聊天 | 继续原有角色和记忆流程 |
| 超出范围 | 写诗、天气查询、通用代码任务、股票分析 | 直接返回商品服务边界提示，不调用模型或商品工具 |
| 需要澄清 | “帮我写一个方案”“给我一点建议” | 询问商品及选购或使用目的，不调用模型或商品工具 |
| 混合任务 | “查这款价格，再写一首诗” | 只把商品部分交给 Agent，最后追加范围说明 |

选中商品本身不会让无关任务变成商品业务。规则保留必要的上下文区别，例如“查询今天的天气”超出范围，而“这款的天气显示功能怎么开启”“这款在雨天能用吗”属于商品使用问题。设备 API、蓝牙接口相关用法与通用代码生成分别处理。

分隔独立任务时保留引号及括号内的文字，引号中的内容作为资料或备注值判断。例如“请记住备注‘今天下雨，写一首诗’”可以正常记录，不把备注值拆成新的天气和写诗任务。括号中的额外任务仍经过范围检查，不能仅凭加上括号而放行。

明确商品问题之后的正常条件、格式要求及验收编号可以继续保留。例如退货问题后的“已经激活了但是没使用过”、容量问题后的“适合几个人使用”，以及“请附引用”等要求。

## 会话、缓存与引用

- 范围拒绝和范围澄清保留会话编号与当前商品编号，返回空引用；HTTP 响应继续使用原有四个字段和 200 状态。
- 原问题和提示保存在 Redis 展示历史中，便于页面显示。它们不写入商品图状态，也不更新商品话题索引，避免越界任务覆盖有效商品话题。
- 用户询问其他型号的天气不会切换当前商品；之后再问“那普通版呢”，仍承接之前的商品话题。
- 混合任务的模型输入、工具问题和图状态只包含保留的商品部分；完整原问题仅用于展示历史及内部执行记录。
- 混合任务继续使用正式工具选择和事实校验。颜色、价格、售后问题仍分别调用专用工具，回答及引用来自实际结果。
- 范围拒绝、范围澄清和混合回答不读取或写入共享答案缓存。普通商品请求保留原缓存行为，避免范围提示进入其他用户的纯商品答案。
- 保留旧版的主动商品切换、商品对比、全库指定型号问答及商品独立记忆。

内部 `trace` 增加 `scope_status` 和 `scope_question`；拒绝和澄清分别记录 `scope_reject`、`scope_clarify`。这些字段不增加到公开聊天响应中。

提示词版本升级为 `product_prompt_v6`，增加服务范围说明，使旧版共享答案缓存失效。

## 人工检查与适用范围

准备好原有模型、商品库和 Redis，重启后端后在同一会话依次检查：

1. 询问 X500 Pro 无线充电，检查商品依据。
2. 查询今天的天气，检查只返回边界提示。
3. 追问“那普通版呢”，检查仍承接无线充电话题。
4. 询问“这款有几种颜色、16+512 多少钱、七天能退吗，再写一首诗”，检查仅回答商品部分、保留业务依据，并显示范围说明。
5. 输入“帮我写一个方案”，检查先询问商品和用途。
6. 记录预算或带引号的备注，再追问备注，检查记忆继续可用。

本次是规则优先的首版范围判断，覆盖已定义的常见问法；未匹配允许或明确拒绝规则的请求返回澄清。任意语言改写、提示词注入和恶意文档指令的抗绕过能力需要另外验收。已有检查点中的历史内容保留，本次隔离规则作用于新的输入。
