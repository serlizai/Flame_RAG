# 圣火项目开发计划 · 企业独立部署与扫码问答版

版本日期为 2026-11-04。本版结合当前代码、既有验收记录和最新需求，作为后续开发建议稿。

本版中的“待实现”和“建议”用于安排后续开发，“已有”表示从当前代码或历史验收记录中核实到的能力。本次核对采用代码与文档审阅，运行结果引用已有验收记录。

## 一、最终交付目标

交付一套企业能够独立部署、导入并维护自身产品资料的商品问答系统。终端用户扫描商品二维码，进入对应企业的商品页面，直接围绕该商品提问。

完整交付包含三部分。

| 使用者 | 需要完成的事情 |
| --- | --- |
| 企业部署人员 | 配置企业信息、模型服务和存储，启动系统，备份与恢复数据 |
| 企业管理员 | 维护商品与业务数据，上传、更新、删除知识文档，发布资料，生成商品二维码 |
| 终端用户 | 扫码进入商品页面，查看商品信息，连续提问，查看回答依据 |

### 1. 已确认的需求

1. 每家公司独立部署一套系统，使用自己的商品数据、知识库和会话存储。
2. 同一种商品或同一型号的多件实物可以共用二维码。
3. 用户扫码后确定当前商品，页面自动展示对应商品信息。
4. 每次问答携带二维码确定的 `product_id`，检索和业务工具都使用这个商品身份。
5. 后端校验该商品在当前实例中存在且可用。企业范围由部署实例及其存储配置确定。
6. 企业能够自行维护数据，后续增加商品通过管理和导入流程完成。

### 2. 本版采用的设计建议

以下细节按便于首版交付的方式安排，后续可以单独调整。

- 将“产品种类”落实为能够明确回答参数、用途和使用方式的一种商品或型号。`product_id` 标识这个对象。
- 扫码问答默认固定当前商品。用户提到其他型号时，引导进入对应商品的扫码页面。
- 保留同一商品的多轮追问。不同商品的历史按商品隔离，重新扫码返回某商品后可恢复它自己的会话。
- 企业公共说明通过明确的适用范围与商品资料一起使用，例如联系方式、适用于当前商品的通用服务说明。
- 首版管理数据采用 SQLite，文档检索继续采用 Chroma，上传先支持约定的结构化模板和 Markdown、TXT 文档。

### 3. 编号的含义

| 名称 | 含义 | 示例 |
| --- | --- | --- |
| 部署地址 | 确定进入哪家企业的系统 | `https://service.example.com` |
| `product_id` | 一种商品或型号的稳定编号 | `flame_kettle_k1` |
| `category` | 商品所属的大类，由商品表提供 | `kitchen_appliance` |
| `sku` | 商品规格的业务编号 | 某容量、颜色或配置对应的编号 |
| `session_id` | 一段用户会话的编号 | 首轮由后端创建，追问时复用 |
| `thread_id` | LangGraph 内部恢复图状态的编号 | 继续按会话与商品生成 |

例如，一批 K1 电热水壶可以使用同一个 `product_id` 和同一张二维码。“厨房电器”属于较宽的分类，仅凭这个分类还无法确定具体商品。

已有十个商品的 `product_id` 可以继续使用。存在多个销售规格时，在当前商品下保存规格和 SKU，报价按具体规格查询。规格缺失且影响答案时，再向用户询问规格。

## 二、系统流程

### 1. 终端用户扫码问答

```text
扫描商品二维码
        ↓
打开该企业的 H5，网址包含 product_id
        ↓
读取当前商品详情，校验商品存在且可用
        ↓
显示商品卡片、快捷问题和聊天框
        ↓
提交 product_id、message、session_id
        ↓
FastAPI 校验请求与当前实例的商品记录
        ↓
恢复当前会话、当前商品的 LangGraph 状态
        ↓
Agent 根据问题调用对应工具
        ↓
整理本轮事实与引用，生成回答
        ↓
保存会话，返回回答、商品身份和引用
```

四个工具分别访问明确的数据来源。

| 工具 | 职责 | 主要数据来源 |
| --- | --- | --- |
| `product_rag_tool` | 使用方法、知识解释、卖点和 FAQ | 当前商品的已发布文档，及明确适用的公共说明 |
| `product_info_tool` | 型号、颜色、规格、容量、功率等结构化事实 | 当前商品信息和规格记录 |
| `price_tool` | 指定规格的价格 | 当前有效的价格记录 |
| `after_sales_tool` | 退换货、保修和服务条件 | 当前商品适用的售后规则 |

混合问题可以调用多个工具。商品身份由后端注入工具，答案中的事实和引用对应本轮实际取得的数据。

### 2. 企业维护数据

```text
管理员登录
        ↓
创建或导入商品、规格、价格、售后数据
        ↓
上传文档并指定适用商品或公共范围
        ↓
校验数据、预览解析结果
        ↓
按章节切分，继承 Metadata
        ↓
生成向量，构建待发布版本
        ↓
检查导入结果，发布新版本
        ↓
生成商品访问链接和二维码
        ↓
用户扫码使用已发布数据
```

企业后续通过同一流程更新资料。导入失败保留上一份可用版本，并显示失败原因和可重试的任务记录。

## 三、扫码入口与接口约定

### 1. 二维码承载内容

二维码保存商品页面的网址，例如以下示意地址。

```text
https://service.example.com/?product_id=flame_kettle_k1
```

该地址中的域名确定企业实例，`product_id` 确定当前商品。文档和价格更新后继续沿用稳定的商品链接。

企业后台支持按商品批量导出二维码和对应名称。使用手机已有扫码能力打开 H5，即可完成用户入口。

### 2. 页面和后端共同遵守的规则

| 情况 | 目标行为 |
| --- | --- |
| 有效商品编号 | 加载该商品详情，允许提问 |
| 编号缺失、空白或 `null` | 页面提示重新扫码，聊天接口返回 422 |
| 商品编号不存在 | 页面显示无效商品提示，接口返回 404 |
| 商品已下架或停用 | 页面显示当前商品不可用，接口返回 404 |
| 商品存在，资料尚未准备好 | 展示商品基础信息，问答明确说明资料暂缺 |
| 商品详情加载失败 | 显示加载失败及重试入口 |
| 对话提到其他型号 | 说明当前商品范围，引导进入对应商品页面 |
| 问题涉及多个规格 | 在当前商品范围内询问影响答案的规格 |

必填商品编号和商品可用性校验在模型加载、缓存读取及工具调用之前完成。检索范围始终从本轮有效商品记录取得。

### 3. 正式接口

| 接口 | 新版用途 | 与当前实现的差异 |
| --- | --- | --- |
| `GET /api/products/{product_id}` | 扫码后获取当前商品的基础信息 | 增加可用状态判断，成为用户页面的初始化入口 |
| `POST /api/chat` | 围绕扫码商品问答 | `product_id` 必填，固定商品范围 |
| `POST /api/chat/stream` | 流式返回商品回答 | 待实现，与普通聊天共用校验和业务规则 |
| `GET /api/health` | HTTP 存活检查 | 已有，继续作为进程探活接口 |
| `GET /api/products` | 商品目录查询 | 已有，可供管理侧目录展示和兼容调用使用 |
| `/api/admin/...` | 商品维护、文档导入、发布和二维码管理 | 待实现，所有管理操作经过管理员认证 |

扫码页面初始化只需调用当前商品详情接口。管理侧对商品的新增、编辑、删除和导入统一走管理员接口。

新版聊天请求示例，省略 `session_id` 表示新会话。

```json
{
  "product_id": "flame_kettle_k1",
  "message": "这款怎么清洗？"
}
```

响应继续沿用 `answer`、`citations`、`session_id`、`product_id` 四个核心字段。后续追问带回返回的 `session_id` 和同一个商品编号。

当前 `follow_conversation=true` 会解析并切换商品。新版扫码模式保留话题承接能力，将商品身份固定为扫码所得的编号。该规则在后端生效，前端与后端一起调整。

旧 GET、POST `/query` 需要纳入迁移安排。公开兼容入口统一执行商品必填和固定范围规则，相关旧调用方与测试同步迁移。接口说明应区分当前行为与升级后的行为。

## 四、数据和存储设计

### 1. 每个实例的数据组成

| 数据 | 当前载体 | 首版交付建议 |
| --- | --- | --- |
| 商品基础信息 | JSON 商品表 | SQLite 商品表，支持批量导入和后台编辑 |
| 规格、价格、售后 | 演示业务 JSON | SQLite 业务表，保留更新时间和适用条件 |
| 原始知识文档 | 本地 Markdown | 实例自己的文档目录及文档登记表 |
| 文本块与向量 | Chroma | 继续使用 Chroma，增加文档及发布版本信息 |
| 导入任务 | 命令行执行结果 | SQLite 任务记录，展示状态、错误和发布结果 |
| 用户聊天记录、答案缓存 | Redis | 继续使用企业实例自己的 Redis |
| LangGraph 检查点 | SQLite | 保留独立的检查点文件及现有线程规则 |

企业部署包明确配置品牌展示、公共访问地址、模型服务、向量模型路径、文档目录、业务数据库、Chroma、Redis 和检查点路径。

当前开发机的 BGE-M3 路径是 `/Users/lwj/AI_project/RAG/models/BAAI/bge-m3`。交付环境通过配置指定自己的模型目录。

各企业的存储目录、数据库文件、Redis 服务和持久化卷分别配置。同一物理服务器上部署两家公司时，也为各实例分配独立的存储资源。

### 2. 商品表与知识库的分工

商品表保存稳定身份、名称、分类、可用状态和规格关系。问答开始前，后端用它校验二维码编号。

知识库保存商品文档的文本块、向量和 Metadata，用于检索相关说明。价格和结构化参数从相应业务记录取得。导入时校验重复出现的关键字段，冲突资料进入待修正状态。

两家企业可以各自拥有 `tea_001`。它们分别连接自己的数据，查询各自的商品记录。聊天请求只需要当前商品和会话信息，企业隔离通过部署配置完成。

### 3. 文档范围与 Metadata

本版建议先支持两类文档。

| 范围 | 绑定方式 | 检索规则 |
| --- | --- | --- |
| 商品文档 | 绑定一个 `product_id` | 只进入该商品的检索结果 |
| 企业公共说明 | 管理员声明适用于全部商品，或关联明确的商品集合 | 仅在适用于当前商品且与问题相关时参与检索 |

公共售后规则由售后数据维护，工具按具体商品规则及公共规则的明确优先级取值。后台在发布前处理冲突，回答同时保留适用条件。

商品文档的 Chunk Metadata 建议如下，字段值仅作结构示例。

```json
{
  "product_id": "flame_kettle_k1",
  "product_name": "Flame K1 电热水壶",
  "category": "kitchen_appliance",
  "scope": "product",
  "document_id": "doc_kettle_manual",
  "document_version": "2",
  "knowledge_version": "release_002",
  "source": "kettle_k1.md",
  "section": "使用说明",
  "chunk_index": 0,
  "chunk_id": "由文档身份、版本、位置和内容生成"
}
```

- 继续保留现有的 `sku_id` 元数据。新文档若针对整个商品型号，可以只绑定商品，具体规格文档再绑定相应 SKU。
- 同一个商品可有说明书、FAQ、保养说明等多个文档，使用不同的 `document_id` 管理。
- 公共文档使用 `scope=company_common`，适用关系由后台登记并参与服务端检索约束。
- 沿用按二级章节切分，再按 800 字符上限、100 字符重叠继续切分的初始参数，后续根据评测调整。
- 检索只读取当前请求所使用的已发布版本，引用保留对应文档、章节和版本。

### 4. 导入、更新与发布

首版导入流程需要完成以下能力。

1. 提供商品和业务数据模板，支持后台填写及批量导入。校验商品 ID、规格、金额、必填字段和文档关联。
2. 支持 Markdown、TXT 文档上传，显示解析预览。企业试用反馈用于确定后续 PDF、Word 的支持顺序。
3. 文档的创建、替换和删除按 `document_id` 定位，商品下架有独立状态。
4. 构建过程中显示任务状态，失败能重试，重复提交能识别为同一次或同一版本操作。
5. 发布时让商品记录、业务数据和向量索引使用一致的版本，保留上一份可用版本用于恢复。
6. 发布完成后更新知识版本，使答案缓存失效。已有会话继续保存，再次询问商品事实时获取最新依据。

当前建库脚本按输入的完整文档集合同步，并清理集合之外的旧块。单文档上传需要增加独立的导入流程，避免把其他文档误判为已删除。

建议首版由后台生成完整待发布资料快照，在独立位置建库并核验，成功后切换发布版本。写入任务顺序执行，每次问答固定使用一个发布版本。后续数据量增大时，再优化为具备同等一致性保障的增量发布。

## 五、Agent、会话与缓存

### 1. 当前商品身份

`product_id` 由入口校验后写入 LangGraph State。商品检索、结构化查询、价格查询、售后查询、引用校验和缓存读取使用同一个身份。

类别从商品表派生，终端用户直接提问即可。当前商品缺少资料时，明确指出缺少的内容，并提供企业配置的联系渠道。

### 2. 多轮对话

- “这款”“它”“怎么清洗”等指代承接当前扫码商品。
- 同一商品追问复用 `session_id`，后端按会话与商品恢复 `thread_id`。
- 点击“新对话”创建新的会话编号。
- 建议浏览器按企业站点和商品保存会话编号，返回同一商品页面时可继续上次对话。
- 切到其他商品页面使用该商品自己的上下文。重新返回原商品时恢复原商品历史。
- 检查点支持服务重启后恢复模型上下文，Redis 保存用户问答记录，二者在交付文档中分别说明。

### 3. 答案缓存

继续沿用只对适合共享的独立首轮问题使用答案缓存的策略。缓存范围至少包含商品编号、问题、提示词版本和已发布知识版本。

价格及其他动态业务问题读取有效业务记录。多轮追问使用本会话上下文。资料更新后，旧答案、旧引用和历史工具结果作为历史保留，新的事实回答以本轮有效数据为依据。

## 七、沿用原周次的新版任务安排

这里保留原版十二周编号，方便对照既有开发记录。已完成部分继续复用，后续按第八节的顺序补齐需求差异。

### 第 1 周 · 项目基础与独立部署配置

- 复用现有服务和目录结构，整理企业品牌、模型、数据目录及服务地址配置。
- 每个实例使用独立的业务数据、知识库、Redis 和检查点存储。
- 补齐新环境初始化流程，管理员可以从空商品库开始导入数据。
- 验收时在两个独立实例中创建同名商品编号，确认回答分别来自各自资料。

### 第 2 周 · 企业商品资料与知识库

- 复用现有切分、Embedding 和 Chroma 检索能力。
- 定义商品、业务数据、文档模板及 Metadata，支持一个商品关联多个文档。
- 建立商品资料与公共说明的适用关系，记录来源及版本。
- 验收文档继承 Metadata、商品范围过滤、公共说明适用性和资料缺失行为。

### 第 3 周 · 扫码确定商品上下文

- 用商品访问链接和二维码确定 `product_id`，保持编号稳定。
- 校验当前实例的商品存在且可用，再写入 State 并注入工具。
- 将商品编号设为必填，统一处理缺号、错误编号和下架商品。
- 验收扫码后直接提问“这款怎么用”，答案与引用均属于扫码商品或明确适用的公共资料。

### 第 4 周 · 商品问答规则与引用

- 提示词读取企业身份和当前商品，约束工具选择及事实来源。
- 固定扫码商品范围，资料不足时说明缺失信息。
- 保留现有引用编号机制，增加来源版本和公共资料适用范围校验。
- 验收价格、售后、知识解释和无答案问题，检查回答与真实工具结果一致。

### 第 5 周 · 正式接口调整

- 复用单商品详情、聊天和健康检查接口，收紧聊天请求中的商品约束。
- 明确用户端接口和管理员接口的职责，提供 Swagger 示例及错误示例。
- 将公开旧 `/query` 入口纳入同一商品范围约束，迁移旧调用方。
- 验收无效请求在调用模型前返回预期错误，合法请求返回商品、会话和有效引用。

### 第 6 周 · 四类工具接入企业业务数据

- 沿用知识、商品信息、价格、售后四类工具及现有组合调用能力。
- 将演示专用业务读取改为可维护的数据访问流程，支持企业导入和更新。
- 明确规格差异、有效报价、售后条件，以及结构化记录与文档冲突的处理规则。
- 验收企业修改价格或售后规则后，问答使用新数据并给出对应依据。

### 第 7 周 · 固定商品的多轮会话

- 保留同商品连续追问、历史持久化和重启恢复。
- 调整现有“普通版”“Pro Max”等自动切换商品逻辑，使扫码身份稳定。
- 增加返回商品页面继续会话、新会话、资料更新后续问的测试。
- 验收各商品上下文独立，新的事实查询使用当前有效数据。

### 第 8 周 · 扫码 H5 与流式回答

- 基于现有 Vue 页面，完成商品详情直达、快捷问题、聊天与引用展示。
- 增加缺号、商品不可用、加载失败和资料暂缺页面状态。
- 完成 `POST /api/chat/stream`，明确增量文本、最终答案、引用、结束和错误事件。
- 流式只展示可公开的回答内容，最终文本与引用经过同一套事实校验。需要固定字段回答或兜底修正的内容在校验后分段发送。
- 验收真实手机扫码、连续提问、引用展开、流式失败提示和最终答案一致性。

### 第 9 周 · 范围约束与异常处理

- 覆盖无效商品、无资料、无对应规格、工具异常和模型超时。
- 校验引用来源、商品范围和资料版本，上传文档中的内容始终作为资料处理。
- 管理操作使用管理员认证，文档上传校验格式、大小和解析结果。
- 验收请求改动、提示词干扰、旧资料引用和工具失败等场景的预期行为。

### 第 10 周 · 企业数据评测与检索优化

- 以企业真实资料建立约 50 至 100 条验收问题，覆盖知识、参数、价格、售后、多轮和无答案。
- 沿用现有评测工具，记录检索命中、工具选择、事实正确性、引用与响应时间。
- 根据评测结果决定是否加入 Reranker，并对加入前后的效果做同集对照。
- 扫码范围、商品身份、价格取值和资料更新属于必须逐项通过的验收场景。

### 第 11 周 · 企业管理后台与数据发布

- 管理员登录、商品和规格维护、价格及售后维护。
- 文档上传、预览、替换、删除、导入状态、发布结果和版本恢复。
- 商品链接与二维码的生成、查看及批量导出。
- 经授权的聊天记录查看，用于企业定位缺失资料和回答问题。
- 验收由企业人员独立完成“新增商品 → 导入资料 → 发布 → 扫码问答 → 修改资料 → 再次问答”。

其中登录、商品维护、上传和发布的最小能力提前开发，与扫码链路一起形成交付基础。

### 第 12 周 · 部署、文档和交付验收

- 准备版本化交付包、配置模板、部署说明、数据模板和管理员操作说明。
- 完成 HTTPS 访问、持久化配置、重启恢复、备份恢复及升级流程。
- 部署说明分别验证进程存活、模型与存储可用、真实商品问答三个层次。
- 使用至少一家企业提供的真实资料，在独立环境从安装到扫码完成整条链路验收。
- 交付时提供源码或约定的运行包、接口说明、验收记录和已知限制。

| 4 | 完善扫码体验、二维码批量导出、会话恢复及 SSE | 手机端完成连续问答、引用展示和异常提示 |

## 九、最终验收清单

| 场景 | 通过条件 |
| --- | --- |
| 同型号多件商品共用二维码 | 扫码进入同一个商品页面，知识和参数一致 |
| 扫码进入 H5 | 自动显示对应商品，能够直接提问 |
| 无商品编号进入页面或接口 | 明确提示重新扫码，接口校验失败 |
| 错误编号、下架商品 | 明确返回不可用状态 |
| 同商品连续追问 | 保持当前商品并正确承接前文 |
| 提到其他型号 | 保持当前扫码范围，给出进入对应商品页面的提示 |
| 同商品存在多个报价规格 | 按指定规格报价，信息不足时澄清 |
| 商品知识和公共说明同时存在 | 仅使用适用于当前商品的资料，引用可核对 |
| 新增商品和多篇文档 | 后台发布后可生成二维码并正确回答 |
| 单文档更新或删除 | 其他商品资料继续可用，相关旧内容退出当前版本 |
| 导入失败、重复提交 | 保留已发布数据，任务状态明确且重试结果一致 |
| 修改价格、政策或商品文档 | 新会话及已有会话的事实查询均使用有效新数据 |
| 重启服务、返回商品页面 | 在有效会话和保留期限内恢复对应商品上下文 |
| 两家公司拥有相同商品编号 | 两个实例分别返回各自资料和业务记录 |
| 管理员上传与维护 | 管理操作经过认证，导入错误能够定位和修正 |
| 真实手机扫码及流式问答 | 页面可访问，回答完整，引用匹配，失败可识别 |
| 备份与恢复 | 商品、资料、已发布索引、业务记录和保留的会话恢复一致 |
| 第三方自助交付验收 | 按交付说明独立部署、导入企业数据并完成扫码问答 |
